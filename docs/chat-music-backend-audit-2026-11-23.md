# 点歌台后端审查

2026-11-23，UTC+08:00。审查对象是 VPS 上由 PM2 运行的聊天网关，以及正式站前端发给它的数据。以下 `server.mjs` 和 `music-manager.mjs` 行号均指 VPS 快照。仓库里的同名管理器行号和实现都有差异。

## 核查依据

- VPS 入口为 `/opt/chat-server/server.mjs`，SHA-256 前缀为 `633f0946a405`。线上 `src/music/music-manager.mjs` 为 `0e83493b20e3`，本地为 `c25d65ab3e53`。结束时复核的两个线上哈希与开始时一致。
- 主站最近成功的部署对应 `f4d4244a`。核对前端协议时查看了该提交，并检查了当前工作区已有改动。
- 在本机临时目录用 VPS 音乐模块运行仓库现有的 57 个音乐测试。仓库版本通过 57 项，线上模块副本通过 52 项。五处差异中，两处是轮播名称改用全角括号，两处是轮播选曲行为，一处是点播音源恢复失败后会直接切走。测试使用模拟曲库，不能换算成线上故障率。
- 用独立临时数据复核选曲、队列和重启竞争。正式房间只读取公开歌单、搜索、状态及服务端代码。侧边栏浏览器核对了正式站显示的收藏总数。没有在正式房间点歌、切歌、洗牌或改设置，也没有做两台物理设备的同步实测。

## 应先处理的问题

| 优先级 | 用户会遇到什么 | 原因、位置与验证 |
| --- | --- | --- |
| 高 | 轮播播过好歌后，可能一直停在空闲 | 现场解析把失败歌曲放回队尾，只有剩余列表彻底为空才开始下一轮。用“一首能播、一首永久无源”的线上模块副本验证，第一次播放好歌，接下来连续四次尝试均没有当前歌曲，坏歌始终是唯一剩余项。线上会间隔 1.5 秒继续尝试。在曲源和歌单不变的条件下，已经播过的好歌无法再次入选。见管理器 993、1098、1234、1247 行。 |
| 高 | 明明第三首可以播，切歌仍会短暂落空 | 现场按下标一次取两首，失败后把这两首移到数组末尾，再用原下标向后走。四首固定顺序 A、B、C、D，仅 C 可播，实测一次现场扫描返回空，剩余顺序为 C、D、A、B。后台预查还有另一个计数问题，失败后执行 `i--`，同一首可以再次被查。两首坏歌、每次模拟耗时 100 毫秒，15 秒虚拟时钟内实际查了 150 次。这里计的是候选解析次数，实际外部请求数受缓存影响。见管理器 1004、1039、1053、1098 行。 |
| 高 | 在「全站收藏」里手动点一首，网关会提示找不到曲目 | 详情接口为返回行临时生成 `position`。点歌时网关查询原始收藏对象，只要收到序号就只按序号匹配。比对实际的 113 条详情与 113 条原始收藏，113 条都没有与之对应的序号。走手动点歌分支会在进入音源解析前失败。随机点歌从原始列表抽取，走另一条路径。普通歌单刷新后同一位置也可能换成另一首，目前网关没有同时校验行号与曲目身份。见网关 1082、3319、4816、4833 行及前端 `playlistClient.ts` 第 631 行。 |
| 高 | 上游短暂超时，会让用户已经排好的多首歌消失 | 待播队列切换时，普通解析把临时异常归为无结果，选择器随即移出队首并记为不可用，继续处理下一首。让两首待播歌的解析同时遇到临时故障，实测两首全部出队并记为 `unavailable`。当前点播曲目也有类似路径，健康检查失败且重新解析抛出临时异常时，会跳离当前点播。其他音源可能稍后恢复。见管理器 1164、1202、1222、1592 行。 |
| 高 | 网关重启后新点歌成功，过一会儿却跳回重启前的旧歌 | 恢复任务异步解析旧音源，返回时直接覆盖当前状态。服务已可接收新请求，提交旧结果前没有检查房间播放状态是否已更新。隔离复现中，新歌已成为当前曲目，放行旧解析后又恢复为旧歌，新歌也不在队列里。见网关 1174、7500 行及管理器 206、220、222 行。 |
| 高 | 音源短暂故障后，同一代理地址在部分设备上可能持续报错 | 用线上代理模块在回环地址测试，将上游设为 HTTP 503，收到的响应为 503，带有 `Cache-Control: public, max-age=86400, immutable, no-transform`。缓存层若按此保存错误，同一地址可在上游恢复后仍返回旧错误。应对 5xx 等临时故障发送 `no-store`，将音频内容缓存策略限于成功响应。已验证响应头，未实测正式 CDN 或浏览器实际缓存时长。见线上 `stream-cache.mjs` 第 451、594、625 行。 |
| 高 | 访客的收藏可能被其他请求改动 | 收藏写接口在身份校验没有得到调用者时，仍接受请求里自报的访客身份来决定修改谁的收藏。添加和移除都有这条路径。写操作应只认经过网关验证的访客或账号身份。依据为网关 1337、3851、3909 行的代码审查，未对线上账号做修改验证。 |

## 多设备、找歌与歌单切换

| 场景 | 代码结论与影响 |
| --- | --- |
| 多设备同时收听与切歌 | 已登录成员按用户键去重，同一账号两台设备不会凭空增加一票。旁观连接初始化的是 `observerId`，统计却读取 `socketId`，后者在网关里没有赋值。多个正在收听的旁观连接会被合并成一个。若房间按实际听众数量决定是否需要投票，就可能在人数超过两人时仍允许直接切。听众展示和可投票人数应分别定义。见网关 1166、4348 附近，管理器 1266 行。 |
| 两台设备同时起播 | 服务端默认给新歌统一安排在 500 毫秒后开始，各端可按服务端时钟定位。当前管理器没有实现网关通过可选调用触发的 `ready` 方法，因此不会等待慢设备缓冲完。弱网设备可能后到并追赶房间进度。此处仅描述协议保证，不给出未经实测的设备间误差。见管理器 33、727 行及网关 4944 行。 |
| 慢速切播遇到换房、掉线或人数变化 | 点击待播中的指定歌曲时，网关把当时的人数作为固定值传入。等待音源返回后，管理器复核当前歌曲及队列，却没有复核操作者是否仍在这个房间、人数是否已跨过投票门槛。请求发出时允许直切，结果可能在条件已变化后提交。指定轮播歌曲已有提交前复核，可以复用那套做法。见网关 4897、4988 行及管理器 1393、1418、1499 行。 |
| 手动搜索没有自动换曲库 | 线上启用了 QQ 和网易云，普通搜索只选顺序第一的提供方。公开搜索实测返回两页，每页 10 首均来自 QQ。QQ 的供应商内部有搜索兜底，但普通搜索结果为空或服务异常时不会再搜网易云。只有已有歌曲身份后，跨平台匹配流程才有机会介入。见网关 3796、3811 行及 `registry.mjs` 第 230、351 行。若希望用户搜到其他已启用曲库里的独有歌曲，需要在搜索入口补上该分支。 |
| 排很久的歌可能拿到过期直链 | 预备好的音源在 25 分钟后通过 `isCached` 决定是否继续复用。该方法遇到直链直接返回真，未检查磁盘缓存或上游可用性。用线上模块和空缓存测试得到 `true`，上游检查次数为零。排队超过复用时间后仍可能把旧地址发给所有设备。见管理器 1152 行及 `registry.mjs` 第 571 行。 |
| 收藏更新与轮播曲库不同步 | 「全部公开歌单」从普通歌单存储枚举，单独生成的「全站收藏」未被纳入。手动选中「全站收藏」时也只取当前前 1000 条。收藏写入成功后没有刷新正在使用它的房间，增删可能要等重载或重新选歌单才生效。当前实查 113 首，1000 条上限尚未触发。见网关 1081、1099、1123、1156、3877、3932 行。 |
| 长期运行的内存增长 | 线上两个房间管理器都传入 SQLite。每次点播或轮播仍把记录追加到内存数组，裁剪却只在没有数据库时执行。持续运行时这部分内存随播放次数增长，房间广播还需要重新整理历史快照。见管理器 413、655、809 行。此处确认的是无界增长路径，本次没有测得由此引起的内存耗尽。 |

## 修复与验收顺序

1. **先让轮播一定能结束一轮。** 每次扫描用固定候选快照，每个条目最多探测一次。明确无源的本轮跳过，临时故障的延迟重试，两种情况都要让其他好歌有进入下一轮的机会。保留队首临时故障、尾部只剩坏歌、四首中仅第三首可用三个回归场景。
2. **让点歌按身份找到用户选的那首。** 收藏和普通歌单都应传递并核验稳定的曲目标识。并发刷新或成员筛选改变位置时，应播放原曲或告知列表已变化。同期收紧访客收藏写权限。
3. **保护已经接受的点歌。** 临时故障保留待播项并限制重试次数。断点恢复、指定待播切歌都应在异步解析结束时检查播放代次、房间和权限。覆盖重启期间点歌、等待期间换房和听众从两人变三人。
4. **按实际发布物跑回归。** 将此次核对过的线上改动与仓库对齐，保留有效的恢复和加速逻辑，再针对部署候选运行音乐测试。之后补齐旁观听众口径、共享收藏刷新、搜索兜底与内存上限。

本次没有发现两个任务相互等待锁释放的证据。已复现的长时间无声有明确的状态循环，即使 PM2 显示在线、WebSocket 仍有响应，也可能持续发生。
