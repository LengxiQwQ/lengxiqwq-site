# 聊天室音乐同步调查与改进方案

日期：2026-11-18（UTC+08:00）

## 结论

当前体验问题主要集中在起播协议、浏览器播放控制、缓存未命中路径和故障恢复，不足以据此认定 VPS 性能差或必须迁回 Cloudflare。

建议保留 VPS 的房间控制，完成“提前准备 → 统一约定时间起播 → 持续校准 → 本机优先恢复”。优先修正确定的故障路径，再完善前后端协议。是否增加音频 CDN，应在音频链路实测后决定。

本次只调查并新增此报告，未修改产品代码、部署、重启、提交或推送。未进入真实房间点歌、切歌或发送消息。

## 调查范围与证据边界

- 主仓 HEAD：`09727b6e`。读取本地 ChatApp、MusicPanel、协议类型和保留的 Cloudflare 实现。没有核对正式站静态 JS 与此 HEAD 是否完全一致。
- VPS：只读检查 `/opt/chat-server/server.mjs`、`src/music/music-manager.mjs`、`registry.mjs`、`qq-music.mjs`、`stream-cache.mjs` 和 `audio-source.mjs`。
- VPS 现场：load average 约 `0.02 / 0.07 / 0.08`，可用内存约 2.6 GB，网关约 143 MB。只是当时快照，不代表历史峰值。
- 本机请求公开健康接口 3 次均为 HTTP 200，首字节约 75、94、62 ms。这只能说明小型控制请求当时正常，不能替代音频吞吐、Range 和首播测试。
- PM2 累计重启计数为 85，本次观察进程已运行约 80 分钟；无法仅据该计数区分部署重启与异常崩溃。
- 缓存目录当时约 497 MB、55 个音频文件。配置上限 500 MiB、150 文件，不能将接近上限本身视为故障。
- 历史错误日志中计得 5 条预取 `terminated`，日志样本没有建立当前版本和故障时刻的对应关系，不据此推断当前失败率。
- 使用独立 Node 进程导入当前 MusicManager，通过原型构造隔离对象，替换解析、广播和切歌回调，验证恢复分支。未构造真实管理器、未读写房间数据、未调用音源服务。
- 未做浏览器实际播放、跨设备录音、iOS/Android 真机、锁屏或弱网验收；下列性能指标均为建议目标。

## 已确认的问题

### 1. 房间计时早于设备音频准备完成

证据：VPS `music-manager.mjs:250–259、302–323、411–458`；本地 `MusicPanel.svelte:1325–1334、1622–1686`。

后端解析出可用地址后，直接以当前时间设置 `startedAt` 并广播。没有客户端准备阶段，也没有未来统一起播时间。服务器当前曲目的缓存预取在广播流程中异步启动，不等待缓存完成；下一首虽有服务器预取，但前端没有对应的下一首准备协议。

前端目标进度是 `Date.now() + clockOffsetMs - startedAt`。因此如果某设备到第 8 秒才获得可播放数据，追到第 8 秒属于现有逻辑的结果。是否立即跳转取决于媒体就绪状态和 seekable/buffered 范围，也可能先从头出声、随后再跳。

必须区分两种产品行为：

- 已经在听的人切到新歌：尽量在准备完成后共同从 0 秒起播。
- 中途加入/恢复收听：追上房间当前进度，不能要求房间为后来者重播。

这解释了“切歌从七八秒开始”的可达路径，但尚未复现用户那次具体现场。第三方解析耗时发生在 startedAt 之前，主要增加等待切歌的时间；不能把所有解析等待都算成丢掉的开头。

### 2. 播放偏差容忍过大，纠正方式容易造成跳动

证据：`MusicPanel.svelte:1622–1638、2125–2154`。

- 250 ms 检查一次，并不代表同步精度为 250 ms。
- 连续播放时，偏差必须大于 2.5 秒才进入纠正。
- 两次纠正至少间隔 6 秒。
- 修正靠直接设置 currentTime，没有小幅调速。
- 正在缓冲、暂停、seeking 或 isSyncingAudio 时不进入该纠正分支。
- 目标不在可用范围时，本次对齐不会执行。

结果：相差 1–2 秒可以长期保留；严重落后时又可能突然跳转并产生额外 Range 读取。调小阈值而不改变纠正策略，可能增加卡顿。

### 3. 缓存准备与客户端请求没有合并

证据：VPS `stream-cache.mjs:89–145、148–185`；`server.mjs:990–1019`。

缓存只在完整下载、校验并写好元数据后可读。`prefetchAudio` 会合并预取任务，但普通播放请求缓存未命中后直接访问上游，不等待或复用该下载。预取并发达到 2 时，新预取直接返回，没有等待队列。

因此服务器正在预取时，多台设备仍可能各自触发上游请求。冷缓存场景更容易出现首包时间和缓冲速度差异。当前缓存键是完整上游 URL 的哈希，临时 URL 改变也可能导致相同媒体重复下载。

### 4. 30 秒总超时覆盖整段音频传输

证据：VPS `stream-cache.mjs:12、154、177、185` 及后续 pipeline。

同一个 30 秒 AbortSignal 覆盖整个请求，包括命中缓存后的文件传输。持续有数据但传输超过 30 秒的请求也可能被中断。这是按传输总时长计时，不是播放到第 30 秒必然停止。

连接、首包、持续无数据、客户端断开和整个任务的资源上限应分别处理。缓存文件传输不应复用上游请求的固定 30 秒预算。

### 5. 单设备报错会影响全房，恢复成功也存在断点

证据：VPS `music-manager.mjs:566–592`；`server.mjs:3857`；前端 `MusicPanel.svelte:1570–1586`。

前端一次 15 秒加载超时就上报曲目错误。后端收到单个设备报告即重新解析：

1. 解析得到新地址：更换全房音源并广播。
2. 解析得到同地址：设置 recoveryAttempted 后直接返回，没有通知设备重试。
3. 解析失败：触发全房下一首。
4. 设置 recoveryAttempted 后，同一首后续错误报告不再处理。

三条主要分支均通过隔离内存验证。此设计把“设备网络问题”和“全房音源失效”混为一谈；弱网设备可能干扰正常设备，同地址恢复又可能让失败设备继续停留在错误状态。

### 6. 控制界面与实际出声状态没有完全对应

证据：`MusicPanel.svelte:1695–1731、1736–1782、2208–2266`；`ChatApp.svelte:2704–2708`。

点击开始后，立即把 isListening 设为 true；真正播放成功靠 playing 事件确认。加载中再点击同一按钮，走的是停止收听分支。部分按钮及移动端状态使用 isListening，不能完整表达加载、被浏览器阻止或实际播放。

现有代码已同步调用 play() 并处理 NotAllowedError，这部分应保留。但首次点歌后的自动开声由异步状态触发，不能保证仍持有用户手势权限；自动恢复监听任意 click/keydown 也不如明确的恢复按钮容易理解。

报告不能将所有“点击不播放”归因于浏览器策略：网络缓冲、失败恢复和按钮语义都可能参与。需要实际错误类型和事件时序才能区分。

### 7. 时钟校准已有基础，可以增量改进

证据：`ChatApp.svelte:861–869、1064–1075、2178–2184、2292–2296`。

已经有 ping/pong、往返时间补偿、较大 RTT 样本过滤和回前台采样；不是完全没有服务器时钟同步。

改进点：起初集中获取多个样本、优先低 RTT 样本；为 ping 增加匹配标识；以 performance.now() 锚定估计服务器时间，避免系统时间调整影响播放；恢复前台后重新校时并立即检查播放头。单纯增加心跳频率无法弥补起播协议缺失和 2.5 秒纠偏阈值。

## 与保留的 Cloudflare 实现对照

- 旧 `chat-worker/src/do/room.ts:4788` 同样使用立即 startedAt，不能认为旧版已有完善的同步起播协议。
- 旧 `chat-worker/src/index.ts:857–928` 音频代理代码没有当前 VPS 这一层 30 秒总传输超时，并返回 `public, max-age=1800`；当前 VPS 为 `private, max-age=120`，同时有服务器本地缓存。
- 缓存响应头不同不等于已证明旧平台 CDN 命中率更高；没有旧版同条件测量。
- 当前 VPS 使用不同的解析流程、音源探测和预取恢复实现，不能只按平台名称比较。建议先修复已确认缺陷，再用同一媒体比较浏览器→VPS、VPS→音源的首包和吞吐。

## 推荐实现

### A. 先消除已确认的故障放大

1. 分离连接/首包超时与传输空闲超时；正常持续传输不因固定 30 秒被切断。仍保留文件大小、并发、速率和闲置连接上限。
2. 本机缓冲失败先有限重试和重新对齐，带退避及次数上限；自动播放拒绝只等待明确用户手势。
3. 后端收到错误报告后独立验证音源，不凭单设备超时立刻全房换源/切歌。多设备错误用独立会话去重，并与服务端探测交叉判断。
4. 无论恢复返回同地址还是新地址，都有明确结果/重试指令；避免一次尝试永久关闭恢复。恢复消息绑定 roomId、playUid、sourceRevision。
5. 页面明确显示“准备中、播放中、正在恢复、点击恢复、失败”；按钮行为与状态一致。取消收听和重试是明确的不同意图。

### B. 完成统一起播协议

推荐状态：`preparing → scheduled → playing`，另有本地 `buffering / blocked / error`。房间时间由服务器决定，各设备不能各自重新定义开始时间。

1. 确定下一首和同一媒体版本，广播准备信息，服务器及已收听设备提前加载。
2. 设备报告可播状态和起点缓冲情况。只统计在线且主动收听的设备，排除暂停、被浏览器阻止和已离线设备。
3. 服务器在有界准备窗口内选择未来 startAt，留足控制消息到达余量；先按约 1–2 秒起播准备预算实验，再按数据调整。不能无限等最慢设备，也不能把所有人无条件等满固定时长。
4. 在同一未来时间从 0 秒起播；准备不足者显示恢复状态，随后追上。中途加入不参与已经确定的起播屏障。
5. 队列正常衔接应在上一首结束前完成准备。临时切歌给出立即反馈，在下一首准备期间可短暂保留旧曲，受准备超时约束。
6. 切歌操作串行化，带命令 ID、播放 ID、状态版本和幂等处理；旧准备任务、旧音源解析和旧错误报告不得覆盖新歌。

不要只将 startedAt 改成未来值：前端必须真正延迟播放到约定时间，否则会提前播放。新旧前端也需要协议版本兼容和渐进启用。

### C. 播放中持续保持同步

- 以真实 audio.currentTime 与估计房间进度比较；界面不能只显示理论房间时间而掩盖实际卡住。
- 小偏差设死区；中等偏差小幅调整 playbackRate 并保留音调；较大偏差或恢复播放时执行一次受控跳转。初始可试验 100–150 ms 死区、约 ±1%–2% 调速和约 1 秒硬纠偏界线，最终以设备测试调整。
- 调速适合缓慢漂移，不能拿它慢慢修复几秒误差。校准后及时恢复 1 倍速。
- 缓冲结束、seeked、回前台和重连后重新对齐，防止一直等待定时轮询。seek 目标不可用时要有明确恢复路径。
- 播放控制逐步抽到独立模块，UI 负责呈现。保留现有常驻 audio 元素，避免抽屉切换和组件生命周期干扰播放；若使用额外预载元素，单独验证 Safari 的手势授权及资源消耗。

### D. 让音频供应更稳定

- 合并同一媒体的冷缓存任务，优先当前曲目和下一首，避免每台设备分别请求音源。
- 缓存标识应包含提供方、曲目、质量/格式和媒体版本，不能只使用短期 URL，也不能只靠歌名或曲目 ID 混用不同文件。
- 同一播放实例必须使用同一媒体版本和时长；换成不同版本的音频不能默认沿用原时间轴。
- 保证 200/206/416、Content-Length、Content-Range 和文件完整性。分段缓存若增加复杂度，先落地有界等待的完整文件缓存；不能让首播无限等待全文件下载。
- 增加缓存命中、解析耗时、首包、缓冲次数、恢复结果和设备偏差统计。记录匿名会话/播放标识，不记录鉴权信息、带签名音源链接或聊天正文。
- 如果同一缓存媒体仍在目标地区明显慢，再考虑让专用音频服务/CDN承担媒体传输，VPS 保留房间控制。架构上先分清控制和媒体责任，现阶段不必为了拆分新增多个服务。

## 验收方式与建议目标

以下是待验证的工程目标，不是目前性能承诺。

| 场景 | 建议验收方向 |
| --- | --- |
| 正常网络、已授权、前台、多设备 | 稳态播放头偏差以 100–300 ms 为目标；先把 P95 控制到 500 ms 内 |
| 已预热的手动切歌 | 点击后立即有反馈；争取约 1–2 秒内共同从头起播，不丢开头数秒 |
| 冷音源或上游慢 | 明确显示准备过程；未安排起播前不假推进新歌时间；达到上限给出确定结果 |
| 一台设备弱网/断网 | 仅该设备恢复；其报错不会导致其他设备换源或切歌 |
| 中途加入/暂停后继续 | 加载后追上当前房间，而非从 0 秒重放 |
| 浏览器自动播放拒绝 | 显示明确恢复入口；下一次有效点击能触发真实播放尝试，不假显示播放成功 |
| 连续切歌、切房间、重连 | 最终播放最新确定状态，无旧请求覆盖和旧歌曲误报 |
| 慢速持续下载超过 30 秒 | 不因固定总时间被人为截断；真正无数据超时仍可退出 |
| 后台、锁屏、回前台 | 分平台记录实际支持范围；恢复时重新校准，不承诺后台定时器精确运行 |

覆盖桌面 Chromium、iPhone/iPad Safari、Android Chrome，以及 Wi-Fi/移动网络组合。记录不少于一批连续切歌样本（建议至少 30 次/主要组合），区分冷缓存、热缓存和弱网，统计 P50/P95，不仅看一次成功。

播放头一致不等于扬声器出声时刻一致，系统音频链路和蓝牙存在额外延迟。若要验收“放在一起听也不明显错拍”，需要同步录音或可识别脉冲的声学对比，不能只截图播放器时间。网页聊天室适合追求低感知偏差，不能承诺所有设备、所有后台状态绝对零延迟。

## 外部行为依据

- [HTML 媒体元素规范](https://html.spec.whatwg.org/multipage/media.html)：play、媒体状态、播放速率及跳转行为。
- [MDN：play()](https://developer.mozilla.org/en-US/docs/Web/API/HTMLMediaElement/play)：播放是异步操作，可能被拒绝，界面应按实际结果更新。
- [MDN：playbackRate](https://developer.mozilla.org/en-US/docs/Web/API/HTMLMediaElement/playbackRate)：支持以播放速率调整进度。
- [WebKit：媒体播放策略](https://webkit.org/blog/6784/)：用户手势与媒体播放限制的设计背景；具体当前系统行为仍以真机测试为准。
